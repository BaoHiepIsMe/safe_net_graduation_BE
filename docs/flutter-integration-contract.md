# SafeNet Flutter Integration Contract

This document is the Phase 15 handoff contract. The generated Swagger document
at `/api/docs` is authoritative for field-level request and response schemas.
All REST paths below are relative to `/api/v1`.

## Authentication and envelopes

- Use a Supabase access token as `Authorization: Bearer <token>` for every
  private REST request and as Socket.IO handshake `auth.token`.
- Auth registration/login/refresh are the only APIs that return session tokens.
- Normal success: `{ "success": true, "message": string, "data": ... }`.
- Cursor-list success keeps `data` and `pagination` at the envelope root.
  `pagination` is `{ limit, hasMore, nextCursor }`; pass `nextCursor` back
  unchanged. Lists without a next page return `nextCursor: null`.
- Some bounded list responses have documented root metadata in addition to
  `data` (for example reminder `horizonEndsAt`).
- Error: `{ "success": false, "error": { "code", "message", "details" } }`.
  Branch on the stable `error.code`, never parse a translated message.
- A `204` response has no JSON body. Dates/times are ISO-8601 strings. IDs are
  UUIDs unless Swagger says otherwise. Unknown request fields are rejected.

### Registration

`POST /auth/register` requires the core account and profile fields, plus an
optional `uiMode` (`adult` or `assisted`):

```json
{
  "email": "user@example.com",
  "phoneNumber": "+84912345678",
  "password": "your-password",
  "fullName": "Nguyễn Văn An",
  "gender": "male",
  "dateOfBirth": "2000-01-15",
  "uiMode": "adult"
}
```

Email is normalized to lowercase and limited to 150 characters to match the
existing profile column. Password length is 8–128; full name is 2–100 after
trimming. Phone must contain a country code and 8–15 digits (no local leading
zero); the backend normalizes a missing `+`. Gender is `male`, `female`, or
`other`. Date of birth must be a real `YYYY-MM-DD` date that is not in the future.
`role` is no longer accepted on registration. Instead, `uiMode` (`adult` | `assisted`)
is optional:

- Age `< 13` (in `Asia/Ho_Chi_Minh`): backend forces `uiMode = "kid"`.
- Age `>= 60` without `uiMode`: backend defaults `uiMode = "assisted"`.
- Otherwise: uses the submitted `uiMode` or defaults to `"adult"`.

The server creates one Supabase Auth user with email, phone, and password using
the server-only admin Auth API, marking both email and phone confirmed (`email_confirm: true`, `phone_confirm: true`).
The database trigger creates profile/settings rows atomically and
copies full name, gender, date of birth, `ui_mode`, email, and contact phone into the
profile. No password is stored in the profile. `profiles.ui_mode` is a presentation
preference only (never used for backend authorization), is returned as `uiMode` by
`GET /profiles/me`, and can be updated via `PATCH /profiles/me` (except users under 13,
who receive `403 UI_MODE_CHANGE_DENIED` if they attempt to switch away from `kid`).

`profiles.id` is exactly the UID generated by Supabase Auth; the Flutter client
does not create another profile or submit an owner/user ID. Profile email comes
from the Auth row, and profile phone comes from the Auth phone normalized to
`+country-code` format. Full name, gender, birthday, and `ui_mode` are passed as metadata
for the trigger. If any required profile/settings insert fails, Auth account
creation rolls back in the same database transaction.

A `201` response has `data.user` containing `id`, `email`, `phoneNumber`,
`fullName`, `gender`, `dateOfBirth`, and `uiMode`; `data.session` is `null`.
No signup confirmation email is sent; after registering, navigate to the login
screen and use the email/password or phone/password login endpoint immediately.
Duplicate email/phone returns `409 USER_ALREADY_EXISTS`.

Deployment requires Prisma migrations `20261016090000_registration_profile_fields`,
`20261110090000_profile_registration_role`, and `20261120090000_care_roles_and_scopes`
before enabling this request contract.
Supabase Auth calls use `SUPABASE_AUTH_TIMEOUT_MS` (default 10000 ms).

### Login

`POST /auth/login` accepts exactly one account identifier with a password:

```json
{ "email": "user@example.com", "password": "your-password" }
```

```json
{ "phoneNumber": "+84912345678", "password": "your-password" }
```

Email is trimmed/lowercased. Phone uses the same international format as
registration; a missing `+` is normalized. Supplying both identifiers, neither,
unknown fields, malformed contacts, or an empty password returns `400`.

Until SMS verification is configured, phone is an identifier for the same
email account. The backend resolves the indexed profile phone, verifies the
current UID/phone/email binding through the Auth admin API, and asks Supabase
Auth to verify the email account's password. It also checks the returned Auth
identity before returning a session. This neither sends SMS nor marks the phone
verified, and it preserves Supabase's email-confirmation checks.
An unknown phone, stale phone binding, or incorrect password returns the same
`401 INVALID_CREDENTIALS` response. An inactive profile returns `403 ACCESS_DENIED`.
Both login methods return the existing `user` and `session` response.

### Profile birthday and UI mode

`PATCH /profiles/me` accepts `dateOfBirth` as a valid `YYYY-MM-DD` calendar
date (or `null` to clear it) and `uiMode` (`kid` | `adult` | `assisted`).
The backend converts the calendar date to a UTC Date for Prisma's PostgreSQL
`date` column. Both `GET /profiles/me` and the PATCH response return
`dateOfBirth` as `YYYY-MM-DD` or `null`, without a time or timezone suffix,
and `uiMode` (`kid` | `adult` | `assisted`) instead of `role`.
If the user's effective age is `< 13` (in `Asia/Ho_Chi_Minh`), `uiMode` is
locked to `"kid"`; attempting to change `uiMode` away from `"kid"` returns
`403 UI_MODE_CHANGE_DENIED`. From 13 on, `"kid"` is refused with the same code.

### Family Care Roles, Scopes, Invitations, and Join Requests

Behaviour source of truth: `docs/roles-and-permissions.md`. Roles are flags on the
membership, not a `role` string. Flutter turns them into text chips ("Chủ nhóm",
"Quản lý", "Được chăm sóc", "Người chăm sóc").

Terms used below:

- **Care Manager**: `canManageCare === true`.
- **Family Admin**: the Owner, or a Care Manager with `isHired === false`.
- **canManage(me, target)**: both accepted in the same active family, I am a Care
  Manager, I am not the target, the target `isCareRecipient`, and if I am hired
  and not the Owner the target id is in my `careScopeMemberIds`.

1. **Member object** (members list/detail, invitations, join approvals, and
   `GET /families/{familyId}/locations/current`,
   `GET /families/{familyId}/members/{memberId}/location`):
   - `familyLabel`: `father | mother | husband | wife | son | daughter | brother |
     sister | grandfather | grandmother | grandchild | caregiver | other`
   - `isOwner`, `canManageCare`, `isMinor` (age `< 18` in `Asia/Ho_Chi_Minh`),
     `isHired`, `isCareRecipient` (`isMinor || is_care_recipient`)
   - `careScopeMemberIds`: member ids; empty unless `isHired`
   - `locationSharingEnabled`: always `true` for a care recipient
   - `role` is gone. Other members' `dateOfBirth` is never returned.
   - `GET /families` and `GET /families/{familyId}` return the caller's own
     membership flags at the family root (`familyLabel`, `isOwner`,
     `canManageCare`, `isCareRecipient`, `isMinor`, `isHired`,
     `careScopeMemberIds`).

2. **Create family** `POST /families` `{ familyName, avatarUrl?, familyLabel, displayName? }`:
   needs a date of birth (`422 PROFILE_DATE_OF_BIRTH_REQUIRED`) and age `>= 18`
   (`403 MINOR_CANNOT_CREATE_FAMILY`). The creator is Owner and Care Manager.

3. **Invite** `POST /families/{familyId}/invitations` (Family Admin):
   `{ email | phoneNumber, familyLabel, displayName?, canManageCare?, isCareRecipient?, careScopeMemberIds? }`.
   - `isCareRecipient` has 3 states: omitted = decided at acceptance by age
     (`>= 60` gives `true`); `true`/`false` = explicit. Under 18 is always a care
     recipient and never a manager.
   - `familyLabel = caregiver` makes the invitee hired with `canManageCare = true`
     and needs `careScopeMemberIds` (at least one current care recipient):
     `400 VALIDATION_ERROR` when missing, `422 CARE_SCOPE_INVALID` when a target
     is not a care recipient of this family. A minor cannot be `caregiver`
     (`422 MEMBER_ROLE_CHANGE_DENIED`). `careScopeMemberIds` on other labels is
     `400 VALIDATION_ERROR`.
   - `GET /families/invitations/pending` items carry the resolved flags plus
     `careManagers` (`id, userId, familyLabel, displayName, isHired, fullName,
     avatarUrl`) so the invitee sees who will look after them.
   - Accepting needs a date of birth (`422 PROFILE_DATE_OF_BIRTH_REQUIRED`).

4. **Join by code** (preview, request, approval; both endpoints throttled 10/min):
   - `GET /families/join-preview?code=` returns
     `{ familyId, familyName, avatarUrl, memberCount, owner: { userId, fullName, displayName, avatarUrl } }`.
     Wrong or expired code: `404 FAMILY_INVITE_CODE_INVALID`.
   - `POST /families/join` `{ code, familyLabel, displayName? }` returns the family
     fields plus `membership` (member object with `status: "requested"`),
     `requestedAt`, `expiresAt`. Needs a date of birth
     (`422 PROFILE_DATE_OF_BIRTH_REQUIRED`). Already a member:
     `409 FAMILY_MEMBER_ALREADY_EXISTS`. Repeating a live request returns the same
     request. The Owner and non-hired Care Managers get a `family_join_request`
     notification (`metadata.memberId`).
   - `GET /families/join-requests/mine` returns `[{ id, familyId, userId,
     familyLabel, displayName, status, requestedAt, expiresAt,
     family: { ...family, owner: { userId, fullName, avatarUrl } } }]`.
   - `DELETE /families/join-requests/{memberId}` returns `204` (requester cancels).
   - `GET /families/{familyId}/join-requests` (Family Admin) returns `[{ id,
     familyId, userId, familyLabel, displayName, status, isMinor, isSenior,
     requestedAt, expiresAt, profile: { id, fullName, avatarUrl, gender } }]`.
   - `POST /families/{familyId}/join-requests/{memberId}/approve` (Family Admin)
     `{ familyLabel?, displayName?, canManageCare?, isCareRecipient?, careScopeMemberIds? }`
     returns the member object. `.../reject` returns the member object with
     `status: "rejected"`. Both notify the requester with
     `family_join_request_processed` (`metadata.decision`: `approved | rejected`).
   - Errors: `404 FAMILY_JOIN_REQUEST_NOT_FOUND`,
     `422 FAMILY_JOIN_REQUEST_INVALID_STATE` (already handled),
     `422 FAMILY_JOIN_REQUEST_EXPIRED` (7 days),
     `403 FAMILY_JOIN_REQUEST_ACCESS_DENIED`.

5. **Update a member** `PATCH /families/{familyId}/members/{memberId}`
   `{ familyLabel?, displayName?, canManageCare?, isCareRecipient?, careScopeMemberIds?, locationSharingEnabled? }`.
   Any accepted member may call it; each field has its own rule. Denials are
   `403 MEMBER_ROLE_CHANGE_DENIED` unless noted.
   - `displayName`, `familyLabel`: yourself, or a Family Admin for others. Only
     the Owner edits the Owner.
   - Moving into or out of `caregiver` (hired) is Family Admin only, and never on
     yourself unless you are the Owner. Leaving `caregiver` also removes
     `canManageCare` (send `canManageCare: true` in the same call to keep it).
     Moving into `caregiver` needs `careScopeMemberIds` (`422 CARE_SCOPE_INVALID`).
   - `canManageCare: true`: Family Admin, adult targets only. `false`: the Owner
     for others, or yourself. The Owner always keeps it
     (`403 FAMILY_OWNER_CANNOT_LEAVE`).
   - `isCareRecipient`: Family Admin, adult targets, never yourself. Turning it on
     also turns the member's sharing on.
   - `careScopeMemberIds`: Family Admin, hired targets only.
   - `locationSharingEnabled`: **only yourself**. A care recipient cannot turn it
     off (`403 CARE_RECIPIENT_CANNOT_DISABLE_LOCATION_SHARING`, also on
     `PATCH /profiles/settings`).
   - Any change to permissions notifies the family with `family_role_changed`.

6. **Transfer ownership** `POST /families/{familyId}/transfer-ownership` `{ memberId }` (Owner):
   the target must be an accepted adult (`422 OWNERSHIP_TRANSFER_TARGET_INVALID`).
   The new Owner gets `canManageCare = true`; a hired new Owner loses the scope
   list (an Owner is never scope-limited). The old Owner stays a Care Manager;
   "Chuyển, thôi quản lý" is a follow-up `PATCH` of their own
   `canManageCare: false`. Notifies the family with `family_role_changed`.

7. **Remove and leave**:
   - `DELETE /families/{familyId}/members/{memberId}` (Family Admin): only the
     Owner removes another Care Manager; nobody removes the Owner
     (`403 FAMILY_OWNER_CANNOT_LEAVE`); a hired Owner cannot remove a care
     recipient (`403 HIRED_OWNER_CANNOT_REMOVE_CARE_RECIPIENT`).
   - `POST /families/{familyId}/leave`: the Owner must transfer first
     (`403 FAMILY_OWNER_CANNOT_LEAVE`); under 18 cannot leave
     (`403 CHILD_CANNOT_LEAVE_FAMILY`). When a care recipient leaves, the people
     who could manage them get `care_recipient_left` (`metadata.priority: "high"`).

8. **What a hired caregiver (not Owner) sees**: current location, location
   history, safe zones and their events, daily status, reminders and phone rules
   only for members in `careScopeMemberIds`. No camera access. They still
   receive SOS from everyone.

9. **Feature gates**: safe zones, reminders, location history and daily status of
   another member need `canManage(me, target)`. Phone rules also need
   `target.isMinor`. Safe-zone alerts go only to the people who canManage the
   member.

### Registration verification

On a development/staging project, opt in with
`RUN_LIVE_SUPABASE_REGISTRATION=true` and run
`npm run test:integration:registration`.
This exercises the real registration service, Auth API, profile trigger,
duplicate-contact handling, transaction rollback, birthday updates, and login
by email or phone (including an unverified phone with a confirmed email). It
creates temporary accounts and deletes them during cleanup. Confirmation-mail
requests are stubbed; it does not send email or SMS or change Auth settings.

## REST domain surface

Swagger contains the complete body, query, parameter, success, and error
schemas for these stable groups:

- `/auth`, `/profiles`, and `/health`
- `/families` and `/families/{familyId}/members`
- `/devices` and `/devices/{deviceId}/locations`
- `/locations` and `/families/{familyId}/locations`
- `/families/{familyId}/geofences`
- `/notifications`
- `/sos` and `/sos/contacts`
- `/reminders`
- `/families/{familyId}/cameras`
- `/phone-management`, family phone-management, and device command endpoints
- `/families/{familyId}/conversations` and `/conversations`
- `/conversations/{conversationId}/calls` and `/calls`
- `/daily-status` and family-member daily-status history

Never send actor/owner IDs, status timestamps, recipients, notification source,
or other server-owned fields unless Swagger explicitly defines them.

## Idempotency keys

Generate a UUID once and reuse it for retries of the same logical action:

- device registration: installation identity defined by its request contract;
- location: `clientLocationId`;
- SOS: `clientRequestId`;
- phone usage/commands: the client request ID defined by Swagger;
- message: `clientMessageId`;
- call initiation: `clientRequestId`.

Reusing a key with a different payload produces a conflict. Network retries
must not generate a new key.

## Socket.IO

Connect to the API origin with `auth.token`. The server joins the authenticated
private room `user:{userId}`. Sensitive producers resolve current recipients
server-side and deliver through private user rooms; Flutter must not request a
broad family room as an authorization shortcut.

Server events:

| Event | Safe purpose |
| --- | --- |
| `location.updated` | Authorized location DTO after commit |
| `geofence.entered`, `geofence.exited` | Safe geofence-event DTO |
| `notification.created` | Persisted notification DTO/identifier |
| `sos.created`, `sos.resolved`, `sos.cancelled` | Authorized incident DTO |
| `phone_command.created` | Wake-up metadata for the exact target device |
| `message.created` | Persisted text message DTO |
| `call.created`, `call.accepted`, `call.rejected`, `call.cancelled`, `call.missed`, `call.ended` | Current Call DTO |
| `call.signal` | Ephemeral bounded WebRTC offer/answer/ICE relay |

`call.signal` is the only client-to-server domain event. Follow
[`call-signaling.md`](call-signaling.md). Reauthenticate/reconnect after token
refresh. REST/DB state remains authoritative after disconnects or missed events.

## FCM

FCM is a wake-up transport, not delivery truth. Supported notification types
are `geofence_enter`, `geofence_exit`, `sos_alert`, `reminder`, `message`, and
`call_incoming`. Data contains safe identifiers such as `notificationId` and a
domain record ID; fetch authorized REST detail before rendering sensitive data.
No FCM payload contains precise SOS coordinates, credentials, tokens,
installation IDs, SDP, or ICE. A push does not prove a phone command completed
or a Call was accepted.

## State machines and time semantics

- SOS: `active -> resolved|cancelled`; terminal states do not reopen.
- Calls: `ringing -> accepted|rejected|cancelled|missed`, then
  `accepted -> ended`. Ring timeout defaults to 45 seconds and is server-owned.
- Phone commands are durable requested work; only the exact active target Device
  may acknowledge terminal execution. Transport success is not completion.
- Reminders use an IANA timezone with `once`, `daily`, or `weekly` recurrence.
  Each reminder has a `priority` (`low|normal|high|urgent`, default `normal`).
  An occurrence log goes `due -> completed|missed`: only the recipient may
  confirm it (`PATCH /reminders/logs/{logId}/complete`), and an occurrence not
  confirmed within 60 minutes becomes `missed`, which cannot be completed.
  `GET /reminders/agenda?date=YYYY-MM-DD&timezone=...` lists one local day for
  the viewer, adding not-yet-reached occurrences as `upcoming` (`logId: null`).
  Managers see the members they manage; a plain recipient sees only their own.
  Every change emits `reminder.log.updated` (the log DTO plus `occurredAt`) to
  the recipient, the creator and the managers.
- Daily Status uses the subject's IANA timezone and the half-open local-day
  window `[midnight, next midnight)`. Reports are immutable non-AI snapshots.

## Privacy and revocation

The database and current server-side relationship state are authoritative.
Pending, rejected, removed, unrelated, archived-family, inactive-device, or
revoked-manager relationships lose access to new protected operations. Passive
location visibility requires global and per-family sharing, except for care
recipients (`isCareRecipient`): they are always visible to their family, and
their own switches cannot hide them. A
manual SOS location snapshot is incident-scoped explicit emergency sharing and
does not change passive sharing settings.

### Sharing controls

`PATCH /profiles/settings` (also returned by `GET /profiles/settings`) carries
three sharing fields:

- `locationVisibility`: `all` (default, every accepted family member) or
  `selected` (only users listed by `/locations/me/viewers`). It applies to
  current location, location history, realtime location events, and geofence
  notifications about the owner. The owner always sees their own data.
- `sharingMode`: `continuous` (default) or `battery_saver`. The BE only stores
  it; the phone decides how often to report (battery saver reports less often).
- `notifyOnZoneExit`: kept for compatibility. Safe zones only watch care
  recipients, and their alerts always reach the people who canManage them.

None of these settings hide a care recipient from their family: in a family
where the user `isCareRecipient`, current location, realtime location, safe-zone
alerts and signal-loss alerts ignore them.

`GET /locations/me/viewers` returns `{ viewerUserIds }`. `PUT` replaces the list
with `{ viewerUserIds }`; every id must belong to someone who shares an active
family with the caller, otherwise `400 VALIDATION_ERROR`. The list is kept when
visibility is `all`, so switching back to `selected` restores it.

### Signal-loss alerts

A sweep runs every minute (disable with `SIGNAL_LOSS_ALERTS_ENABLED=false`). It
creates a `location_signal_lost` notification for the other accepted family
members of a sharing user whose last accepted location is older than 8 minutes
(`continuous`) or 25 minutes (`battery_saver`), once per silence. The phone
reports every 2 minutes (10 in battery saver); alerts for iOS devices are
skipped until iOS tracks in the background.

`metadata.reason` is `no_connection` (the device heartbeat is stale too) or
`no_location` (the app is alive but sends no position). Both are guesses about
the cause. `metadata` also has `memberId`, `lastLocationAt`, `lastSeenAt`,
`latitude`, `longitude`. With `locationVisibility=selected` only the chosen
viewers are told. The owner can opt out with `notifyOnSignalLost=false` in
`PATCH /profiles/settings`. In a family where the owner is a care recipient, the
alert always goes to the people who canManage them, whatever these settings say.

### Safe zone icon

Geofences accept and return an optional `icon` (`home`, `school`, `work`,
`shop`, `hospital`, `other`, or `null`). Clients show a default icon for `null`.

### Emergency location

Emergency location is independent of location sharing. When the user triggers
SOS, Flutter takes one fresh GPS fix (it still needs OS location permission)
and sends it in `POST /api/v1/sos` as optional
`location: { latitude, longitude, accuracy?, recordedAt }`. This applies even when
global or per-family sharing is off.

- If `location` is sent, the SOS event stores it as its own snapshot. It is
  never written to location history, `current_locations`, the Family Map, or
  `location.updated`.
- If it is omitted, the server falls back to the last tracked current location.
  That location may be stale or missing when sharing is off.
- `location` is excluded from the SOS idempotency fingerprint. A retry with the
  same `clientRequestId` and a slightly different fix reuses the original event
  and keeps its original location.

Fall events will follow the same rule once the fall model and ingestion API
exist: the detector attaches its own one-shot fix to the fall event.
`fall_events.latitude`/`longitude` already exist for this.

## Explicitly unavailable or unverified

Phone fall AI and camera fall AI are deferred. Automatic fall-to-SOS, camera
streaming/playback, TURN, server media relay, recording, and screen sharing are
not implemented. Actual peer-to-peer voice/video and Android/iOS phone-policy
enforcement require Flutter/device integration and are not verified by this
backend.
